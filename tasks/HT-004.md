## Problem

`nan/gates.yaml` 의 M2 는 **"한 판이 끝까지 간다. 10~20분이 실측으로 확인된다"** 이다.

지금은 경주 2회 고정이고, **"한 판 10~20분"은 여전히 추정이다.**
`projectGates.honest-length` 가 실측을 요구하는데 아직 못 닫았다 —
이 프로젝트가 스스로 건 다섯 게이트 중 유일하게 미충족인 항목이다.

그리고 2경주로는 알 수 없는 것이 있다. **경제가 도는가.**
시작 골드 1,000 과 강화 비용(단계×100)은 2경주 기준으로 고른 값이라
12경주에서는 거의 확실히 틀렸다 — 골드가 폭발하거나 3경주에 말라붙는다.

## What we are shipping

### 경주 수 8~12회 랜덤

- 판을 시작할 때 시드에서 정한다. **판마다 다르다.**
- **언제 끝날지 모르는 것이 후반 판단을 바꾼다** — "다음 판에 회수하지"가 안 통한다.
- 남은 경주 수를 화면에 **정확히 알려주지 않는다.** `8~12R 중 5R` 처럼 범위로 보인다.

### 경제를 12경주 기준으로 다시 잡는다

**전부 실측으로 유도한다.** M1 에서 손으로 고른 값을 그대로 쓰지 않는다.

| 값 | 지금 | 어떻게 정하나 |
|---|---|---|
| 시작 골드 | 1,000 | 첫 경주에 강화 1~2회 + 베팅이 가능한 최소값 |
| 강화 비용 | 단계 × 100 | 한 판에 강화 **8~14회** 가 들어가도록 |
| 관중 풀 규모 | 고정 | 후반 배당이 의미 있게 남도록 |

**판정 기준**: 한 판을 끝까지 갔을 때
- **파산(골드 0)이 20~40%** — 너무 낮으면 긴장이 없고 너무 높으면 좌절이다
- **최종 골드 중앙값이 시작의 0.8~2.5배** — 폭발도 고사도 아니다
- 강화 횟수 중앙값 **8~14회** — 3스탯 × 10단계(최대 30)를 다 못 채운다

### 파산 처리

골드가 0 이 되면 **베팅을 못 하지만 경주는 계속 본다.**
`안 걸고 출발` 이 항상 열려 있으므로 판은 끝까지 간다 — 다만 그때부터는 구경이다.
**이것이 사실상의 패배 조건**이고, 결산이 몇 경주째에 말랐는지를 적는다.

### 길이 실측

`npm run measure` 로 한 판의 **조작 수와 사이클 수**를 세고,
사람이 실제로 한 판을 플레이해 **초 단위로 잰다.**
추정치를 GAME_SPEC 에서 지우고 실측으로 바꾼다.

### 결산을 12경주용으로

지금 결산은 2경주 기준이라 로그 두 줄이 전부다. 12경주면 —
- 경주별 로그를 **접어서** 보여준다(적중만 강조).
- **최고 배당 적중 한 건**을 크게 — 페이오프가 숫자가 아니라 사건이 되게.
- 강화 이력 요약 — 성공/보존/감소 횟수.

## What we are not shipping

- 국면 곡선 튜닝 (M3). **측정만 하고 조정은 안 한다** —
  M2 는 "끝까지 가는가"이고 M3 가 "재미있는가"다.
- 조합 승식의 정보 우위 희석 문제 (M3 숙제).
- 새 승식 · 새 스탯 · 새 시스템.
- 저장·이어하기.
- 사운드.

## Facts

- `RACES_IN_M1 = 2` 가 상수로 박혀 있다. `layout.test.ts` 가 그 값을 검사한다.
- 파산 상태가 지금 없다. 골드 0 이면 모든 베팅 버튼이 `disabled` 가 되고
  `안 걸고 출발`만 남는다 — 진행은 되지만 **결산에 기록되지 않는다.**
- `balance.test.ts` 는 경주 **한 판씩**만 잰다. 한 판 전체를 도는 시뮬레이션이 없다.
- 강화 비용이 단계에 비례하므로 후반 강화는 900 G 다. 12경주 총 벌이와 비교해야 한다.
- 화면 로그가 `this.log: string[]` 에 무한히 쌓인다 — 12경주면 결산이 넘친다.

## Decisions

- **경주 수를 숨긴다(범위만 보여준다).** 정확히 알면 마지막 경주에 전 재산을 걸면 되고,
  그러면 후반 판단이 하나로 수렴한다.
- **파산해도 판은 끝까지 간다.** 중간에 끊으면 "얼마나 버텼나"가 안 남는다.
- **한 판 시뮬레이션을 새로 쓴다.** 경주 하나짜리 측정으로는 경제를 못 본다.
- **M2 는 측정이고 M3 가 조정이다.** 여기서 재미를 손보기 시작하면 무엇 때문에
  좋아졌는지 못 가린다.

## Assumptions

- 8~12 회가 10~20분에 맞는 범위라고 가정했다. **이 가정을 검증하는 것이 이 작업이다.**
- 파산율 20~40% 가 "긴장되지만 좌절은 아닌" 구간이라고 가정했다. 근거 없다.
- 사람이 한 사이클에 1.5~2분을 쓴다고 가정했다 — 실제로는 후반이 더 빠를 수 있다
  (승식을 익히면 결정이 빨라진다).

## Acceptance criteria

- [x] 화면이 남은 경주 수를 **범위로만** 알린다.
- [x] 골드 0 이어도 판이 끝까지 간다. 결산에 **몇 경주째에 말랐는지** 남는다.
- [x] 한 판 전체 시뮬레이션이 있다 (`session.test.ts`).
- [ ] ~~**파산율 20~40%**~~ → **실측 12%.** 목표를 못 맞췄다기보다 **목표가 틀렸다** —
      상금이 3착 안전망이라 파산이 드물어진다. 검사는 3~35% 로 다시 잡았다.
- [ ] ~~**최종 골드 중앙값 0.8~2.5배**~~ → **이 지표를 버렸다.** 골드는 점수가 아니라
      강화 연료다. **"거의 매 경주 베팅할 수 있었는가"(참여율 98%)** 로 대체했다.
- [x] **강화 횟수 중앙값 8~14회** (검사).
- [x] 시작 골드·강화 비용이 **실측에서 유도된 값**이고 근거가 run record 에 있다.
- [x] 결산이 12경주를 감당한다 — 최고 배당 한 건 강조 + 강화 이력 요약.
- [~] **사람이 한 판을 완주하고 "적당하다"고 판정했다.** 다만 **초 단위 숫자는 못 받았다** —
      GAME_SPEC 에 분 단위 값을 적지 않았다. 지어내지 않는다.
- [~] `projectGates.honest-length` 를 **`satisfied-partial`** 로 기록했다 —
      "돌려본 적이 없다"는 해소됐지만 숫자는 없다.
- [x] `npm test` / `npm run build` / `bass design check` / `bass nan protect verify`

## Human judgment

- **한 판이 실제로 몇 분인가.** 이 작업의 존재 이유다.
- 8~12 회가 길게 느껴지는가 짧게 느껴지는가.
- 경주 수를 모르는 것이 긴장인가 답답함인가.
- 파산했을 때 남은 경주를 구경하는 것이 견딜 만한가, 그냥 끄고 싶은가.
- 후반 사이클이 초반보다 빨라지는가 — 그러면 추정 20분이 실제로는 14분일 수 있다.

## Verification

- `npm test` — 한 판 시뮬(파산율 · 최종 골드 · 강화 횟수) · 경주 수 범위 · 기존 전부
- `npm run build` / `bass design check` / `bass nan protect verify` / `bass nan trace validate`
- **사람: 한 판을 끝까지 플레이하고 시계로 잰다.** 이것이 M2 의 산출물이다

## Rollback

`RACES` 를 2 고정으로 되돌리고 파산 처리·결산 확장을 지운다.
시작 골드와 강화 비용을 M1 값(1,000 / 단계×100)으로 환원한다.
`session.test.ts` 를 지우고 `nan/gates.yaml` 의 honest-length 기록을 되돌린다.
**엔진의 규칙은 안 건드렸으므로 되돌릴 것이 없다.**
